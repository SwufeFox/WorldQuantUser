# 快速回测方法论

同时记录**有效出分速率、完整证据速率和机制级产出**。它们回答不同的问题，不能互相替代。
日常只用 `campaign` 调度、`ledger analyze` 复盘；完整操作路径见
[批量回测与台账复盘](ledger-workflow.md)。本页补充性能与并发的测量口径。

## 一、开局就用对照，别先铺量

每个假设开跑前写三件事：预期方向、起效时间、什么结果会推翻它。

首轮只要两臂：原基线和只改一处的处理组，两者锁同一股票池、同一训练窗、同一样本。

字段可用性先做一次有界审计（PIT 时间、财报期间、覆盖度）。对不齐就归档，省下整轮额度。

## 二、发单前去重，QUICK 后再晋级

去重键是四元组：表达式 + 有效设置 + 数据窗口 + 模拟模式。少一个就会重复投。

QUICK 只做筛选，看训练期对照增量、成本后表现、双边持仓广度。

只有通过的组才拉日 PnL、转 FULL，复核逐年稳定性、留出期、平台相关性。

## 三、单队列持续补位

优先让能回答同一个问题的对照臂一起完成，不要让对照组跨批次漂移。

记录受理、终态、有效出分三个时间点，按 `Retry-After` 回收，父任务到终态才补位。

超时先用原回执恢复，不要重投。

包大小按「同地区同模式下的有效出分率 + 尾部耗时」实测选，在途批次也要计入观察。

## 四、命令分两层

spec 定义**跑什么**，`campaign run` 定义**怎么调度**。

```bash
python research_cli.py campaign run \
  --watch --batch-size 4 --multi-size 8 \
  --max-wait-seconds 55 --interval 20 \
  --defer-quick-pnl --prefer <spec> --stream
```

| 参数 | 作用 |
| --- | --- |
| `--batch-size 4` | 本次调用的本地并发预算；native Multi 下按父任务计 |
| `--multi-size 8` | 每个原生批次带几条子回测 |
| `--max-wait-seconds 55` | 每次调用的共享等待预算 |
| `--watch --interval 20` | 持续回收，20 秒一轮 |
| `--defer-quick-pnl` | QUICK 先出分，晋级时按 Alpha ID 补 PnL |
| `--prefer` / `--stream` | 指定优先 spec / 输出逐条调度事件 |

手动兜底两个入口：未发完用 `probe --resume`，已受理只等结果用 `probe --recover`。

上面的 4 和 8 是示例预算，不是平台容量承诺。四个父任务各带八个子请求，表示
四个父任务 reservation 携带三十二条臂，不能据此推断平台同时执行三十二条回测。
同一父任务的子请求必须使用相同设置；工具按完整设置拆包。

## 五、提速有没有用，看这张表

| 观察到 | 优先查 |
| --- | --- |
| 有空槽、队列里也有活 | 预检、调度、回收之间的空转 |
| 槽位全满、受理后等待拉长 | 平台耗时，比较同条件分包表现 |
| 出分多、完整对照少 | 补对照臂，砍同机制变体 |
| QUICK 过得多、FULL 晋级少 | 拆淘汰原因，看 QUICK 漏了什么 |

## 六、只用当前证据约束并发

账号在途槽位、POST 突发速率、进程内 worker 数、native Multi 父任务数分别记录。
历史一次 burst 测量不能变成所有账号永久的并发上限。

`machine_lib.concurrency_plan` 是账号预算的共同入口：显式预算是本地选择；只有当前账号
匹配且已验证的容量证据可以下调它。缺失或过期的证据保留为未知，不主动联网猜测容量。
`batch_quick.py` / `pipeline_pc.py` 也复用这套规则，`--concurrency` 控制 worker 数，
`--account-slots` 控制共享账号预算。HTTP 429 按已有 `Retry-After` 路径退避，不据一次
限流永久改写容量。已受理任务继续通过原检查点恢复。

native Multi 仍有客户端自己的父任务与包大小边界；这是实现边界，不等于测得的账号容量。
优先复用一个调度进程及会话，避免多个 worker 重复认证。

## 七、报告吞吐量时带上分母

`execution.finished` 表示完成状态且至少有一项有效数值指标，可能仍缺 checks 或日 PnL。
测量一次运行时，记录起止快照，分别报告新增出分、完整 checks、待补 PnL 和失败数；
恢复的旧结果与新提交的结果分开，不能直接拿最终累计数除以本次运行时间。

父任务检查点保存受理时间、最近一次观测到等待的时间、首次观测到终态的时间。
最后一项是客户端观测时间，不是服务端精确完成时间。把平台等待和本地回收耗时分开，
再比较同地区、同模式、同包大小下的持续吞吐量。
