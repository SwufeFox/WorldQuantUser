# 快速回测方法论

衡量标准是**每小时裁决多少组假设**，不是每秒发多少请求。

机器按有效请求算吞吐，研究按独立机制算产出——同一机制换一百个窗口，仍然只回答一个问题。

## 一、开局就用对照，别先铺量

每个假设开跑前写三件事：预期方向、起效时间、什么结果会推翻它。

首轮只要两臂：原基线和只改一处的处理组，两者锁同一股票池、同一训练窗、同一样本。

字段可用性先做一次有界审计（PIT 时间、财报期间、覆盖度）。对不齐就归档，省下整轮额度。

## 二、发单前去重，QUICK 后再晋级

去重键是四元组：表达式 + 有效设置 + 数据窗口 + 模拟模式。少一个就会重复投。

QUICK 只做筛选，看训练期对照增量、成本后表现、双边持仓广度。

只有通过的组才拉日 PnL、转 FULL，复核逐年稳定性、留出期、平台相关性。

## 三、单队列持续补位

优先让能回答同一个问题的对照臂一起完成，不要让对照组跨批次漂移。

记录受理、终态、有效出分三个时间点，按 `Retry-After` 回收，父任务到终态才补位。

超时先用原回执恢复，不要重投。

包大小按「同地区同模式下的有效出分率 + 尾部耗时」实测选，在途批次也要计入观察。

## 四、命令分两层

spec 定义**跑什么**，`campaign run` 定义**怎么调度**。

```bash
python research_cli.py campaign run \
  --watch --batch-size 8 --multi-size 8 \
  --max-wait-seconds 55 --interval 20 \
  --defer-quick-pnl --prefer <spec> --stream
```

| 参数 | 作用 |
| --- | --- |
| `--batch-size 8` | 并发父任务槽上限 |
| `--multi-size 8` | 每个原生批次带几条子回测 |
| `--max-wait-seconds 55` | 每次调用的共享等待预算 |
| `--watch --interval 20` | 持续回收，20 秒一轮 |
| `--defer-quick-pnl` | QUICK 先出分，晋级时按 Alpha ID 补 PnL |
| `--prefer` / `--stream` | 指定优先 spec / 输出逐条调度事件 |

手动兜底两个入口：未发完用 `probe --resume`，已受理只等结果用 `probe --recover`。

## 五、提速有没有用，看这张表

| 观察到 | 优先查 |
| --- | --- |
| 有空槽、队列里也有活 | 预检、调度、回收之间的空转 |
| 槽位全满、受理后等待拉长 | 平台耗时，比较同条件分包表现 |
| 出分多、完整对照少 | 补对照臂，砍同机制变体 |
| QUICK 过得多、FULL 晋级少 | 拆淘汰原因，看 QUICK 漏了什么 |

## 六、踩过的坑

本地回收从约 48 秒压到 14 秒，仍然卡在「平台槽位全满、长时间没有新出分」。

提速必须同时看两段时间：本地拿到回执多快，平台生成回执多快。只优化前者会撞天花板。

并发不是越高越好：单账号实测能吃 11 槽，但进程数 ≥3 会打满 `/api/authentication`（5 次/分钟），表现为「Incorrect authentication credentials」的假失效。**一个进程，把批次合到一份 arms 文件里。**

去重的收益远大于提并发：2076 臂里大量是同一机制的回看期/decay/中性化变体，按机制压到 400 以内，比并发从 8 提到 11 划算得多。

最省额度的动作通常不是跑得更快，是**更早知道哪组实验不值得继续**。
